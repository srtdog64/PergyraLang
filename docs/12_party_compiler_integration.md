# Party / Role Compiler Integration

Last updated: 2026-05-25

This document records the current party/role/roster compiler contract. The old
standalone `party_compiler.h` FiberMap proposal has been removed because it was
not included by the build and did not own any implemented compiler path.

## Current Contract

Party support is not a separate compiler subsystem. It is part of the normal
front-end and backend ownership spine:

- parsing owns `AST_PARTY_DECL`, `AST_ROLE_DECL`, and `AST_ROSTER_DECL`;
- semantic checking owns party, role, roster, ability, and authority validation;
- DIR/RIR/MIR declaration inventory owns hosted method metadata;
- C and LLVM backends consume hosted-method views and shared host declaration
  compatibility policy;
- runtime scheduling or FiberMap-style plans are future runtime/module work,
  not beta compiler source of truth.

The stable compiler question is:

> Which subject or class satisfies a role slot, which abilities are required,
> and which hosted methods must be emitted consistently by C and LLVM?

The compiler must not answer that question by reopening ad-hoc party scans in
each backend emitter. Backend paths consume the same host declaration
compatibility table used for class, enum, relation, effect, zone, world, party,
role, and roster declarations.

## Lowering Shape

The implemented lowering is intentionally conservative:

1. Parser builds the party/role/roster AST.
2. Semantic checking validates role slots, ability references, and authority
   relationships.
3. Declaration inventory records hosted methods and owner metadata.
4. C/LLVM emitters request a hosted-method view from the declaration inventory.
5. If required MIR metadata is absent on a frozen path, codegen reports a hard
   missing-inventory diagnostic instead of silently regenerating behavior from
   AST shape.

This keeps party integration aligned with the beta source-of-truth rule:
semantic facts are owned once, then consumed by later stages.

## Not Beta Surface

The following older design ideas remain outside the beta compiler contract:

- standalone `PartyTypeInfo` extraction APIs;
- static FiberMap C template generation;
- compile-time scheduler affinity tables;
- GraphViz party visualizers generated by the compiler;
- parser hook registration APIs;
- party templates with const-generic sizes.

Those ideas may return as module/runtime ecosystem work after the core compiler
spine is frozen. They should not reappear as unused public headers.

## Drift Gates

The current regression contract is:

- `mir-declaration-inventory-test-smoke` must keep party/role/roster in the
  shared host compatibility set;
- `type-resolution-resolver-inventory-test-smoke` must keep semantic owner
  seams from reopening recursive lookup paths;
- backend compare fixtures must keep hosted party/role/roster methods emitted
  consistently by C and LLVM.

If party scheduling becomes a beta feature later, it must enter through a
runtime/module design and then add explicit AIR/MIR evidence. It should not
revive standalone compiler-only FiberMap APIs.
