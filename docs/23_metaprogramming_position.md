# Pergyra 메타프로그래밍 입장 (설계 결정)

## 결론: 템플릿 메타프로그래밍(TMP)을 넣지 않는다

## 배경

C++ 템플릿 메타프로그래밍은 "런타임 비용 0으로 컴파일 타임에 코드를 생성"하는 기법이다.
`std::enable_if`, SFINAE, `constexpr if` 등으로 타입에 따라 다른 코드 경로를 만든다.
본질적으로 "제네릭 + 조건부 컴파일"을 극단까지 밀어붙인 것.

### TMP의 대가

- 에러 메시지가 수백 줄 (C++ 악명의 주범)
- 코드가 읽기 불가능 (`template<template<class...> class>`)
- 컴파일 시간 폭발
- 상위 5% 개발자만 제대로 사용 가능
- C++도 Concepts(C++20)로 TMP를 줄이려고 20년을 싸웠음

## Pergyra가 TMP 없이 같은 문제를 푸는 방법

| C++ TMP의 역할 | Pergyra 대안 | 상태 |
|----------------|-------------|------|
| 타입별 코드 생성 | 제네릭 monomorphization (`Pair<Int>` → `Pair_Int`) | 구현 완료 |
| 조건부 타입 분기 | ability/role dispatch (런타임 vtable) | 구현 완료 |
| 정책 주입 (Policy pattern) | ability + role 조합 | 구현 완료 |
| CRTP (정적 다형성) | role이 subject에 바인딩 | 구현 완료 |
| Type traits | 제네릭 constraint (`where T: Comparable`) | 파서 완료, 시맨틱 TODO |
| 컴파일 타임 계산 | 향후 `const` 표현식으로 충분 | 미구현 |

이 조합으로 실용 범위의 95%가 커버된다.

## "코드가 코드를 생성한다"에 대한 입장

개념 자체는 흥미롭지만, **TMP는 올바른 접근이 아니다.**
TMP는 "타입 시스템의 우발적 튜링 완전성"이지, 의도된 기능이 아니었다.

### 조건부 컴파일이 필요한가?

대부분의 경우 **필요하지 않다.** Pergyra에서 조건부 동작이 필요한 시나리오:

- **플랫폼별 분기** → 빌드 설정 또는 `#[cfg]` 스타일 어노테이션으로 충분 (언어 문법이 아닌 빌드 도구)
- **타입별 분기** → ability dispatch가 이미 해결
- **기능 플래그** → 빌드 타임 상수 (`const DEBUG: Bool = true`) + if로 충분, dead code elimination이 제거

### 향후 "코드 생성"이 필요해지면

TMP 대신 **더 깨끗한 대안**이 있다:

1. **컴파일 타임 코드 변환 플러그인** (Rust의 `proc_macro` 모델)
   - 언어 문법을 오염시키지 않음
   - AST → AST 변환을 별도 도구로 분리
   - 에러 메시지가 명확 (플러그인이 직접 생성)

2. **소스 생성기** (Go의 `go generate` 모델)
   - 빌드 전에 외부 도구가 `.pgy` 파일을 생성
   - 생성된 코드가 일반 코드와 동일하게 컴파일
   - 디버깅이 쉬움 (생성된 파일을 직접 읽을 수 있음)

3. **어노테이션 기반 코드 생성** (Java annotation processor 모델)
   - `@Serialize`, `@Route` 같은 선언이 코드 생성을 트리거
   - Pergyra의 structured comment (`/// @effects`) 시스템을 확장하면 자연스러움

## 설계 원칙

> **Pergyra는 코드가 코드를 생성하는 대신, 계약이 코드를 제약한다.**

- ability는 "이 타입이 무엇을 할 수 있는가"를 제약
- role은 "어떻게 이행하는가"를 구현
- zone은 "누가 누구에게 무엇을 할 수 있는가"를 검증
- effect는 "이 동작이 어떤 부작용을 가지는가"를 추적

이 계층이 TMP가 하려는 "컴파일 타임 코드 선택"을 대부분 대체한다.
