# 공유 그래프의 소유권과 연결 분리 설계

검토일: 2026-10-08. 상태: **DESIGN PROPOSAL / 제한 모델 증명, 구현 OPEN**.
기준: `3658548d24bca3d721e4f1974ac7a10da99f7aa8`의 미커밋 작업 포함 트리.

**소유자가 하나라는 조건은 참조도 하나여야 한다는 뜻이 아니다.**
일반 값의 값 의미론은 유지하고, 실제 객체 identity가 필요한 그래프에는
한 소유 영역 안의 여러 비소유 링크를 제공하는 방향을 검토한다.
사용자가 링크마다 Slot이나 정수 인덱스의 수명을 관리하게 만들지 않는다.

최초 범위는 사용자가 요청한 설계 방향의 기록이었다. 후속
[28번 통합 계약](../semantics/28_memory_boundary_composition.md)은 기존 owner들을
연결하는 요건을 채택하지만, 이 제안의 구체 문법·MIR 스키마나 구현 착수 승인은
아니다. 현재 자동 cleanup 구현 순서는
[구현 지침](../agent_work_directives/ownership_clean_implementation_2026-10-08.md)을
유지하며, 이 제안으로 별도 병렬 구현 트랙을 열지 않는다.

## 제안의 출처와 기여 구분

**Qt의 방식을 가져와 Pergyra에 적용하자는 구상은 사용자가 제안했다.**
AI가 독자적으로 발견한 구상이 아니다. Qt의 부모·자식 소유 트리와
비소유 참조의 무효화가 출발점이며, AI의 기여는 검토·형식화·레드팀·수정이다.
Qt의 공식 설명은 [Object Trees & Ownership](https://doc.qt.io/qt-6/objecttrees.html)와
[QPointer](https://doc.qt.io/qt-6/qpointer.html)에 있다.

Slot 권한·대여, 루트/노드의 별도 세대, 외부 owner의 footprint 검사와
컴파일러 자동 정리는 Pergyra에 맞춰 검증해야 할 추가 의무다. 아래의 Qt 대응은
설계 유사성이지 Qt 내부 자료구조·비용이나 모든 안전 보장을 그대로 옮겼다는
주장이 아니다. 일반 값의 liveness·move/copy 알고리즘 전체의 출처도 아니다.
현재 공통 비용·한계는
[28번 계약](../semantics/28_memory_boundary_composition.md#tradeoffs-and-limits)에 둔다.

## 소유 관계와 연결 관계

개념 예시이며 현재 Pergyra 문법이나 실행 가능한 예제가 아니다.

```text
소유: 문서 → { A, B, C }
연결: A ↔ B, A → C, B → C
```

문서가 세 노드의 저장소를 소유한다. 연결은 같은 노드를 여러 곳에서 가리킬
수 있지만 소유권이나 해제 책임을 복제하지 않는다. 따라서 연결 관계에는
공유와 순환이 있어도 소유 관계에는 중복 owner나 소유권 순환이 없어야 한다.

문서의 수명이 끝나면 연결 간선을 따라 재귀적으로 해제하지 않는다.
소유한 노드와 backing의 목록을 기준으로 각각 한 번 정리한다. 링크에서
더 이상 도달하지 않는 노드도 개별 삭제 전까지 이 목록에 남아야 한다.
목록 누락은 허용하지 않으며, 전체 정리가 상수 시간이라는 보장도 하지 않는다.
노드별 자원 finalizer가 있다면 기존의 관찰 가능한 정리 의무를 지켜야 한다.

## 사용자 표현과 내부 안전 기제

사용자는 부모와 자식, 양방향 링크, 관찰자 목록처럼 목적에 맞는 관계를
작성한다. 컴파일러는 어느 owner에 속한 링크인지와 허용된 사용 범위를
추론하는 것을 우선한다. 수명이 다른 owner 사이의 링크나 권한 경계는
명시적 계약이 필요하며, 추론 불가능한 관계를 무조건 허용하지 않는다.

Slot은 실제 resource, authority, lifecycle 경계에 쓰는 구성체다.
내부 링크마다 공개 Slot을 강제하지 않는다. 단순 그래프 알고리즘에
subject/action/relation/zone을 장식처럼 추가하지도 않는다. 이 문서의
연결 관계는 도메인 키워드 `relation`과 동일한 의미가 아니다.

구현 후보는 다음 조건을 만족해야 한다.

- 링크는 owner의 identity와 노드 소속을 보존하며 owner의 수명을 암묵적으로
  연장하지 않는다. 외부 대여가 살아 있는 동안 owner를 정리할 수 없어야 한다.
- 읽기 공유와 수정 권한을 분리한다. 수정 진입 경계에서 배타성을 확보하되,
  그 안에서도 동시에 살아 있는 중첩 read/write 또는 write/write 별칭은 막는다.
  owner에 대한 수정 권한 하나만으로 모든 별칭 안전성이 증명되지는 않는다.
- 주소 안정성과 대여 수명이 증명된 구간만 직접 참조할 수 있다. 개별 삭제나
  저장소 이동을 허용하는 장기 링크에는 owner identity와 세대를 검증하는
  핸들이 후보가 된다. 검증 핸들도 수명 전체나 데이터 경쟁의 증명을 대신하지 않는다.
- 삭제 뒤 남은 링크는 해제된 저장소에 접근하지 못해야 한다. 현재 대여를
  어떻게 막고 오래된 링크를 어떤 명시적 실패로 처리할지는 별도 계약으로 정한다.
  ID 재사용과 세대 소진을 포함하며 unchecked wraparound는 허용하지 않는다.
- 그래프 밖으로의 escape, async/worker 전달, FFI 보관은 실제 owner 이동이나
  독립 snapshot 등의 계약을 요구한다. raw pointer 전달이나 숨은 깊은 복사로
  경계를 우회하지 않는다. snapshot의 링크 identity 재구성도 증명 대상이다.

이 방식은 링크를 자연스럽게 표현하려는 방향이지, 무제한 공유 수정이나
검증 비용 0을 약속하는 방식이 아니다. 내부 핸들의 구체 ABI와 source 표기는
아직 정하지 않았다. 일반 Array 등의 D1 복사 정책도 바꾸지 않는다.

## 오래 살아 있는 그래프의 회수 경계

창이나 문서가 끝날 때 그래프 전체를 정리하는 것과, 그 owner가 계속 살아
있는 동안 쓰이지 않는 부분을 회수하는 것은 다른 문제다. 연결이 끊겼다고
노드의 수명이 끝났다고 단정할 수 없다. 다른 링크나 외부 대여가 남을 수 있다.

이 제안은 owner 종료 시 전체 정리와 계약에 따른 개별 삭제를 다룬다.
임의의 공유 그래프에서 고립된 순환까지 자동으로 발견해 회수하는 알고리즘을
제공하지 않는다. 그것에는 추가 수명 증거나 도달 가능성 분석이 필요하다.
owner 안에 남은 노드를 모두 계속 보유하면 정리는 안전할 수 있어도 메모리가
계속 증가할 수 있다. 최대 보유량과 개별 삭제 비용을 별도로 검증해야 한다.

그래프 전체를 owner의 footprint로 잡는 것만으로 각 노드의 마지막 사용 즉시
회수가 증명되는 것도 아니다. 내부 보유량, 링크 검증, 깊은 정리 지연과
snapshot 복사량을 측정해야 하며 GC 대비 성능 우위는 아직 주장하지 않는다.

## 필요한 모델 확장과 반례

현재 [Ownership Clean](../semantics/27_ownership_clean.md)은 일반 값의
이동, 복사, 마지막 사용 정리를 다룬다. 저장된 참조를 다루지 않으므로,
이 제안은 기존 정리의 이름만 바꾸어 적용할 수 없다. owner footprint와
비소유 연결을 분리한 참조 모델, 접근 권한, 삭제와 escape의 의미가 필요하다.

후속 Rocq 검토에서는 고유한 owner 소속, 링크가 owner가 아니라는 조건,
유효 접근의 대상 생존, 중첩 별칭의 배타성, owner 정리의 정확히 한 번 실행,
삭제와 재사용의 명시적 실패, source 관찰 보존을 함께 다뤄야 한다.
현재 `OwnershipCleanCore.v`나 `SlotCalculus.v`가 이 전체 모델을 증명했다는
주장은 하지 않는다.

| 검증 입력 | 입증하거나 반박할 조건 |
|---|---|
| 양방향 링크와 같은 노드의 다중 참조 | 연결마다 복사하거나 정리하지 않으며 owner 종료 때 노드는 각각 한 번 정리됨 |
| 외부 대여가 남은 상태에서 owner 정리 | 유효한 대여를 무효화하는 정리는 거부됨 |
| 노드 삭제 뒤 같은 ID 재사용 및 세대 소진 | 오래된 링크는 새 노드로 바뀌지 않고 명시적으로 거부됨 |
| 다른 owner의 동일 노드 ID 및 동시 수정 별칭 | 잘못된 소속이나 겹치는 수정은 거부됨 |
| backing grow와 async/FFI escape | 이전 주소와 대여가 몰래 유효하다고 취급되지 않음 |
| 장기 owner에서 고립된 순환을 반복 생성 | owner 종료 정리를 자동 중간 회수로 오인하지 않고 보유량 증가를 드러냄 |

수명 종료 단위, 개별 삭제 정책, 경계 밖 identity와 snapshot 의미를 먼저
결정해야 한다. 그 뒤 생산 진입점부터 마지막 접근 및 정리 소비자까지의
전체 사슬을 조사하고 구현 계획을 정한다. 현재 문서화는 이 단계의 완료나
self-host/SoT 폐쇄가 아니다.

## 기존 계약과 연구 참고

[WO-REG 전략](../197_region_arena_strategy.md)의 현재 구현은 인증된 transient
String의 할당 경로다. 일반 그래프 저장소나 recursive aggregate 정리를
이미 제공한다는 근거로 사용하지 않는다. arena는 가능한 내부 할당 방식이지
사용자가 링크마다 넘기는 allocator 표면이 아니다.

[Slot capability 계약](../semantics/08_slot_capability_calculus.md)의 세대와
pin 검증은 관련된 안전 기제지만 저장된 그래프 참조 전체의 증명은 아니다.

[GhostCell 논문](https://plv.mpi-sws.org/rustbelt/ghostcell/paper.pdf)은
데이터와 접근 권한을 분리하고 arena를 사용해 내부 공유와 순환 그래프를
안전하게 다루는 연구 선례다. 설계 참고이며 Pergyra에 API, 수명 표기나
증명을 그대로 도입했다는 뜻은 아니다.

## Rocq 검토 결과 (2026-10-08, Claude)

검토 파일: [`OwnershipGraphLinks.v`](../semantics/proofs/OwnershipGraphLinks.v)
(SHA-256 `6045e9ea9efca71327bc0e49f454bc63b500858caf1633b42ecad300688eefda`).
Rocq 9.3.0과 `rocqchk`로 확인했고 가정은 0개다. 전체 증명 코퍼스 63개도
통과했다(`.tmp/rocq93_ownership/kernel-graphlinks-claude.log`).
canonical 기계에서는 블록, `alloc`, `free`만 가져온다. 그 기계에 명령을
더하지 않으며, 구현이나 계약을 채택한다는 뜻도 아니다.

**결론: 방향은 맞다.** 소유자는 저장소 하나이고, 링크는 아무것도
소유하지 않는 값 `(저장소 id, 슬롯, 세대)`다. 이 구조에서 순환과 다중
참조는 소유권을 복제하지 않는다. 다만 아래 결정을 지킬 때만 그렇다.
결정마다 그것을 어기는 반례를 같은 파일에 실행 가능한 형태로 두었다.

| 위 검증 입력 | 결과 | 근거 |
|---|---|---|
| 양방향 링크와 다중 참조 | 정리 시 블록마다 정확히 한 번 해제한다. 링크 복사와 순환은 힙에 영향이 없다 | `ginv_step`, `drop_releases_exactly`, `cycle_store_drop_frees_each_once` |
| 외부 대여 중 owner 정리 | owner 정리, 그 노드 삭제, 겹치는 쓰기 대여를 모두 거부한다 | `drop_refused_while_borrowed`, `borrowed_store_is_kept` |
| 삭제 뒤 같은 슬롯 재사용과 세대 소진 | 오래된 링크는 영원히 명시적으로 거부되며 새 노드로 바뀌지 않는다. 링크는 발급마다 유일하다 | `stale_forever`, `delete_makes_stale`, `issued_links_unique`, `delete_then_reuse` |
| 다른 owner의 같은 슬롯과 동시 수정 별칭 | 링크가 저장소 id를 담으므로 소속이 섞이지 않는다. 쓰기 대여는 다른 대여와 공존하지 않는다 | `borrow_exclusive`, `relative_edge_in_wrong_store` |
| backing grow와 escape | 대여 중 성장은 거부된다. 정리된 저장소의 링크는 영원히 거부되며 id는 재사용하지 않는다 | `borrow_table_live`, `unguarded_grow_dangles`, `drop_makes_stale` |
| 장기 owner에서 고립된 순환 반복 생성 | 보유량은 슬롯이 가진 노드 전부다. 도달 가능성과 무관하게 남는다 | `heap_is_store_footprint`, `unreachable_nodes_retained` |

**모델이 강제하는 설계 결정**

1. owner 정리는 슬롯 목록을 따라가며, 간선을 따라가지 않는다. 간선을
   따라 해제하면 A↔B 순환에서 A를 두 번 해제한다
   (`naive_edge_drop_double_frees`).
2. 세대는 순환하지 않는다. 최대 세대에 닿은 슬롯은 은퇴시키고 다시
   쓰지 않는다. 나머지 연산으로 세대를 돌리면 삭제된 링크가 새 노드로
   되살아난다(`wraparound_resurrects`). 대가로 은퇴 슬롯은 테이블에
   남는다(`retired_slots_grow_table`). 테이블을 압축하면 링크가 깨지므로,
   이 잔여량은 세대 폭으로 조절할 비용이다.
3. 직접 참조는 대여 범위 안에서만 쓴다. 대여 중에는 그 저장소의 성장,
   대여한 노드의 삭제, 저장소 정리를 거부한다. 성장은 테이블을 옮기고
   옛 테이블을 해제하기 때문이다(`unguarded_grow_dangles`).
   **빈 슬롯 채우기는 대여 중에도 허용된다.** 테이블을 옮기지 않고 대여된
   슬롯을 건드리지 않기 때문이다(`free_slot_insert_under_borrow`). 처음
   모델은 대여 중 삽입을 모두 거부했는데, 이렇게 완화해도 같은 불변식이
   증명된다. 주소가 움직이지 않는 분할 저장소를 쓰면 성장 제한도 없앨 수
   있다. 이 후보는 증명하지 않았다.
4. 노드 안의 간선은 저장소 상대값 `(슬롯, 세대)`로 둔다. 저장소 id는
   저장소 밖 링크에만 담는다.
   - snapshot은 상대 간선을 그대로 유지한다
     (`snapshot_preserves_relative_edges`). 대신 모든 노드를 복사하는
     비용을 낸다(`snapshot_copies_footprint`).
   - 간선을 절대 링크로 저장하면 snapshot의 내부 간선이 원본을 가리키고,
     원본을 정리하면 끊긴다(`absolute_internal_edge_dangles`).
   - 상대 간선을 다른 저장소에서 읽으면 무관한 노드를 가리킨다
     (`relative_edge_in_wrong_store`). 노드를 저장소 사이에서 옮기면 안 되는
     이유다.
5. 삭제가 없는 저장소에서는 발급된 모든 링크가 해석된다
   (`append_only_links_resolve`). 세대 검사를 생략할 수 있고, 남는 것은
   저장소 생존뿐이다. 문서, 컴파일러 IR, 한 프레임의 GUI 트리처럼
   통째로 버리는 그래프는 이 경로로 검사 비용이 0이 된다.

**한계: GC와의 진짜 차이**

- 살아 있는 owner 안에서 링크가 끊긴 노드와 고립된 순환은 회수되지
  않는다. 그대로 남는다는 것이 증명된 사실이다. 장기 그래프는 개별
  삭제를 명시하거나, 프레임·요청·문서 단위처럼 수명이 짧은 owner로
  나눠야 한다. 자동 중간 회수는 이 모델의 범위가 아니다.
- 삭제가 있는 저장소에서는 링크를 해석할 때마다 런타임 세대 검사를 한다.

**모델 밖**

- async, worker, FFI로의 escape를 다루지 않는다.
- 관찰 가능한 finalizer를 다루지 않는다.
- 저장소 사이 노드 이동을 다루지 않는다.
- snapshot은 순수 함수일 뿐 기계 연산이 아니다.
- 대여는 컴파일러의 정적 검사가 정제해야 할 ghost 상태다. 런타임 대여
  계수기를 뜻하지 않는다.
- 저장소를 일반 값으로 소유했을 때 `OwnershipCleanCore`의 drop과 합성되는
  성질은 아직 증명하지 않았다.

이 결과로 위 "수명 종료 단위, 개별 삭제 정책, 경계 밖 identity와
snapshot 의미"의 기본값을 다음처럼 제안한다. 채택은 아니다.

- 수명 종료 단위는 저장소다.
- 개별 삭제는 세대 검사가 있는 저장소에서만 허용한다.
- 경계 밖 identity는 저장소 id를 포함한 링크로만 표현한다.
- snapshot은 상대 간선을 보존하는 깊은 복사로 정의한다.

## 통합 계약 후속 (2026-10-08, GPT)

사용자는 Slot·자동 정리·비소유 그래프를 한 수명 계약으로 연결하기로 했다.
[28번 계약](../semantics/28_memory_boundary_composition.md)은 한 저장소 owner,
owner에 묶인 접근 권한과 한 정리 edge를 요구한다. 구체 저장소 표현·snapshot
기본값을 위 제안에서 자동 채택하지는 않는다.

`tests/coq/MemoryBoundaryCompositionAudit.v`는 기존 GraphLinks와 Core 및 Slot
proof를 사용한다. 명시적인 root/footprint 대응, 두 불변식, 대여 없음과 Slot
release guard 아래에서 그래프 drop과 canonical drop의 결과 힙·정리 footprint가
일치하고 같은 Slot root가 release될 수 있음을 검증한다. 이는 해당 전제 아래의
제한된 결합 결과다. 위 "일반 값으로 소유했을 때의 전체 합성"은 binding 발급,
source 실행·관찰 보존과 실제 runtime 연결까지 아직 증명한 것이 아니다.
생산 구현·원자성·escape와 owner 내부 자동 중간 회수도 계속 OPEN이다.

## 재사용 보강 (2026-10-08, Claude)

사용자 지적: 재사용이 불가능한 모델에서는 재사용 안전을 증명한 것이 아니다.
위 결과의 모델은 노드 블록을 항상 새 이름으로 할당했다. 그래서 다음처럼
보강했고 결론은 유지된다.

- **할당기를 적대적으로 바꿨다.** 저장 공간이 필요한 연산은 쓸 블록을
  인자로 받는다. 서로 다르고 지금 살아 있지 않은 블록이면 무엇이든
  허용하며, 직전 단계에 해제된 블록도 허용한다. 모든 정리를 이 조건에서
  다시 증명했다(SHA-256 `8dba4bc6...`).
- **B의 블록 (4, 0)을 그대로 D에 다시 쓴다.** B의 옛 링크는 거부되고 D의
  링크는 해석된다(`reused_blocks_do_not_revive_link`). 같은 주소를 기억하는
  링크는 아무 실패 없이 D를 읽는다(`address_identity_confuses_reuse`).
  **저장 위치는 식별자가 아니다.**
- 대여 중 성장의 반례도 강해졌다. 옛 테이블 주소에 새 노드가 들어가므로,
  대여는 끊긴 주소가 아니라 다른 객체를 가리킨다(`unguarded_grow_dangles`).
- **저장소 id도 재사용 대상이다.** 이 모델의 id는 다시 발급되지 않는다.
  세대 없이 다시 발급하면 옛 링크가 새 저장소의 노드를 읽는다
  (`store_id_reuse_resurrects`). 구현은 둘 중 하나를 골라야 한다.
  - id를 다시 발급하지 않고, 소진되면 실패로 닫는다(Slot id 런타임과 같다).
  - 링크를 세대가 있는 루트 핸들에 묶는다(감사 파일의
    `rooted_link_refused_after_root_reuse`).

같은 날 SlotCalculus와 메모리 경계 감사 파일도 같은 기준으로 고쳤다.
결과는 [문서 28](../semantics/28_memory_boundary_composition.md)의
"Bounded formal evidence" 절에 있다.

## 해체 정리: 노드 단위 소유 (2026-10-08; 검증 기록 작성: Claude)

Qt 적용 제안자는 사용자이며, 이 절의 작성자 표기는 검증 기록의 작성자를 뜻한다.
아래 29개 정리와 비용 설명은 당시 모델 판의 기록이다. 후속 감사의 현재 경계와
[공통 트레이드오프](../semantics/28_memory_boundary_composition.md#tradeoffs-and-limits)를
함께 읽어야 하며, 당시 모델의 한계를 구현의 완료 사실로 읽지 않는다.

사용자 판단: 고아 노드가 생기는 순간 사실상 실패다. 위 모델처럼 저장소가
노드 전부를 소유하면, 아무 링크도 가리키지 않는 노드가 저장소가 끝날 때까지
남는다(`unreachable_nodes_retained`). 사용자 제안은 Qt의 QObject 트리를
추상화하는 것이다. 소유는 노드마다 하나이고, 해제는 항상 성공하며, 해제할 때
해체 정리로 링크를 정리한다.

검토 파일: [`OwnershipTeardown.v`](../semantics/proofs/OwnershipTeardown.v)
(당시 SHA-256 `6b8e1711fc53b1b1fa54f04ab48fb5dcad9e9337e66b5334f83e2799444da0d4`).
Rocq 9.3.0으로 컴파일했고, 핵심 정리 29개의 `Print Assumptions`는 모두
"Closed under the global context"다(Axiom, Admitted 없음). 독립 레드팀을 두 번
돌렸고, 두 차례 지적(아래 "레드팀 반영")을 모두 고친 판이다.

후속 전체 경로 검토·모델 개선은
[해체 레드팀/국소 갱신 감사](ownership_teardown_redteam_locality_2026-10-08.md)에
기록했다. 그 판은 중복 없는 은퇴 목록, 실제 이전 행만 제거하는 갱신과
무관한 목록 공유를 검증했다. 이 절의 29개 정리·해시는 당시 판의 기록이다.
해제 권한/활성 loan·pin, 탈출 가능한 루트 ID, 지역 Link 접근과 물리적
finalizer/동시성은 그 기록만으로 해결됐다고 볼 수 없다. 자식 색인의 unit 일치
증명도 실행 가능한 indexed walker·성능 상한 증명이 아님을 후속 감사에 명시했다.

이어 [루트 세대·지역 읽기 개선](ownership_teardown_root_epoch_2026-10-08.md)에서
세대 없는 루트 연산을 제거했다. 할당·재부착·해제가 모두 현재 루트 세대를
확인하고, 해제 시에만 증가시키며 재선언은 초기화하지 않는다. 저장된 지역
Link에도 실제 checked read를 추가했다. 이 단일 forest 정체성 증명이
해제 권한, 안정된 loan·pin, arena 경계나 물리 해제까지 증명한 것은 아니다.

**모델.**
- 노드의 소유자는 살아 있는 루트 하나 또는 부모 노드 하나다. 소유는 자식의
  owner 필드이므로 "소유는 하나"가 구조로 강제된다. 링크는 `(슬롯, 세대)`이고
  아무것도 소유하지 않는다.
- 루트는 수명이 있는 프로그램 변수다. `RootNew`로 생기고, 스코프를 벗어나면
  `RootDrop`이 그 루트가 소유한 것 전부를 해체한다. 선언되지 않은 루트에 매달린
  노드는 존재할 수 없다(`RootsLive`).
- 역방향 색인은 각 노드로 들어오는 저장된 링크 목록이다(Qt의 객체별 연결
  목록). 자식 색인은 소유자별 목록이다. 부모 노드의 자식 목록(Qt의 children
  목록)과, 루트가 직접 소유한 노드 목록이 같은 색인에 있다.
- 모든 연산은 대상 노드(새 부모 포함)를 세대가 맞아야 하는 핸들로 지정한다.
- 연산: 루트 생성·해제, 할당(빈 칸 아무 데나, 즉 재사용), 링크 쓰기, 부모
  바꾸기(조상 검사 포함), 노드 해제.
- 해제는 두 단계다. 1단계에서 해제 단위 U로 들어오는 저장된 링크를 색인으로
  찾아 비운다. 2단계에서 U의 칸을 반환하고 세대를 올린다. 두 색인에서 U의
  항목도 지운다.

| 확인한 것 | 결과 | 근거 |
|---|---|---|
| 고아 없음 | 살아 있는 모든 노드는 아직 스코프 안에 있는 루트에 속한다. 몇 단계를 거쳐도 유지되고, 루트가 하나도 없으면 살아 있는 노드도 없다 | `inv_steps`, `every_node_has_live_root`, `no_roots_no_nodes` |
| 루트 수명 | 루트가 스코프를 벗어나면 그 루트가 소유한 노드는 하나도 남지 않는다. 같은 루트 이름을 다시 선언해도 빈 상태로 시작하고 옛 노드를 넘겨받지 않는다 | `root_drop_frees_exactly`, `root_drop_leaves_nothing_owned`, `root_reuse_adopts_nothing` |
| 끊긴 저장 링크 없음 | 저장된 모든 링크가 해석된다. 몇 단계를 거쳐도 유지된다 | `links_never_dangle`, `release_clears_incoming` |
| 해제는 항상 성공 | 살아 있는 노드와 살아 있는 루트에는 정확한 해제 단위가 항상 있으므로 해제 단계가 항상 있다. 결과는 단위를 어떻게 나열했는지와 무관하다 | `release_always_succeeds`, `root_drop_always_succeeds`, `teardown_deterministic` |
| 해제 범위 | 노드 해제는 소유 서브트리 전부를, 살아 있는 노드만 해제한다 | `release_frees_exactly_subtree`, `release_frees_only_live` |
| 해제 단위 계산 | 노드 해제 단위와 루트 해제 단위 모두 자식 색인을 따라 닿는 노드와 정확히 같다. 힙을 훑을 필요가 없다 | `unit_from_kids`, `root_unit_from_kids` |
| 들어오는 링크 찾기 | 역방향 색인이 정확하면 1단계는 U로 들어오는 링크를 전부, 그것만 찾는다 | `index_finds_every_incoming`, `release_field_effect` |
| 재사용과 옛 핸들 | 해제된 칸은 바로 다시 쓸 수 있다. 해제된 노드의 옛 핸들로는 그 뒤 어떤 연산도 일어나지 않는다. 두 번째 해제, 쓰기, 그 밑에 붙이기가 모두 해당하고, 칸이 재사용된 뒤에도 같다 | `released_slot_reusable`, `released_handle_never_acts`, `dropped_root_handles_never_act` |
| 실제 실행 | 빈 힙에서 루트가 A를, A가 B를 소유하고 A와 B가 서로 링크한다. 루트를 놓으면 아무것도 남지 않고, 재사용된 칸은 옛 핸들을 거부한다 | `full_run_cycle_released` |

루트에서 도달 가능성을 계산하지 않는다는 것은 정의에서 나온다. 해체는 경로를
계산하지 않는다. 다만 U 밖의 색인 목록도 고친다(출발점이나 자식이 U에 있는
항목). 모델은 모든 목록을 걸러 내고, 런타임은 U의 필드와 부모 포인터를 따라가면
된다. 비용 상한은 증명하지 않았다.

**규칙마다 반례.** 규칙 하나를 빼면 바로 깨진다.

1. 1단계를 빼면 저장된 링크가 끊긴다(`no_clear_dangles`).
2. 색인에서 항목 하나가 빠지면 그 링크가 끊긴다(`stale_index_dangles`).
   색인은 Qt 연결 목록처럼 정확해야 한다.
3. **해체 정리는 조상 검사를 대신하지 못한다.** 노드를 자기 후손 밑에 붙이면
   소유 순환이 생기고, 그 묶음에는 루트로 가는 경로가 없다
   (`unchecked_attach_orphans`). 해제·이동·루트 해제는 모두 루트에 닿는 대상을
   요구하므로, 이후 어떤 단계도 이 묶음을 해제하거나 다시 붙일 수 없다. 원래
   루트를 놓아도 마찬가지다(`ownership_cycle_permanent`). 붙이는 시점의 조상
   검사가 이를 거부한다(`checked_attach_refuses_cycle`). 해제 거부가 아니라
   붙이기 거부이므로 "해제는 항상 성공"과 충돌하지 않는다.
4. **링크 수를 수명으로 쓰면 순환이 영원히 남는다.** 같은 힙 위에 참조 계수
   기계를 따로 정의했다. 루트가 있을 때는 A와 B 모두 닿는다. 프로그램이 루트를
   놓으면 둘은 닿지 않지만, 서로의 링크 때문에 계수가 1로 남는다. 이후 어떤
   참조 계수 단계도 둘을 해제하지 못한다(`rc_cycle_permanent`). 같은 행동,
   즉 루트를 놓는 것에 대해 소유 모델은 전부 해제한다
   (`full_run_cycle_released`).
5. 해체 도중, 두 단계 사이에서 U로 링크를 거는 날것의 쓰기는 끝나고 나서
   끊긴다(`finalizer_relink_dangles`). 해체가 끝난 뒤에는 같은 쓰기가 거부된다
   (`relink_into_released_refused`). 규칙은 "해체 도중 U로 새 링크를 만들지
   않는다"이다. finalizer를 해체가 끝난 세계에서 돌리는 것은 이를 보장하는 한
   가지 방법(충분 조건)이다. 1단계 이전의 일반 쓰기는 1단계가 지운다. finalizer
   자체는 모델의 연산이 아니다.
6. 해제 단위에서 자손 하나를 빠뜨리면 그 자손이 고아가 된다
   (`inexact_unit_orphans`). 부모 칸을 재사용하면 그 고아가 무관한 새 노드의
   자식으로 조용히 편입된다(`orphan_adopted_by_reused_slot`). 소유 포인터의
   ABA다. 그래서 자식 색인은 정확해야 한다. 정확한 단위는 자식 색인이 주는
   단위이고, 자손까지 해제한다(`exact_unit_frees_descendant`).

**대가와 한계**

- 링크 필드는 다른 곳의 해제로 비워질 수 있다
  (`release_empties_incoming_field`). 그래서 링크 필드 타입은 비어 있을 수
  있음을 드러내야 한다. Swift의 `weak`가 optional인 것과 같은 이유다.
- 저장된 링크를 쓸 때마다 역방향 색인을, 부모를 바꿀 때마다 자식 색인을
  갱신한다. 부모 바꾸기는 조상 검사 비용(깊이만큼)이 든다.
- **소유됐지만 아무도 가리키지 않는 노드는 남는다**
  (`owned_but_unlinked_is_kept`). 고아가 아니라 주인이 붙잡고 있는 것이고,
  주인이 해제하거나 그 루트가 스코프를 벗어나면 해제된다. 추적 GC도 도달
  가능하지만 필요 없는 객체는 남긴다. 다만 오래 사는 루트 하나에 모든 노드를
  매달면 위의 저장소 모델과 같은 문제가 그대로 돌아온다. 소유 간선은 실제로
  노드를 붙잡는 필드여야 한다.
- 해제 권한: 모델은 해제를 "세대가 맞는 핸들을 가진, 루트에 닿는 노드"로만
  제한한다. 주인만 해제할 수 있다는 것(복제할 수 없는 소유 핸들)은 타입
  시스템의 몫이다. 더 넓은 단계 관계에서 forest/저장 링크 불변식이 유지돼도
  caller의 해제 권한이 증명되는 것은 아니다. 활성 loan·pin도 이 모델에는 없어
  "해제는 항상 성공"을 실제 자원 해제의 무조건 허용으로 해석하지 않는다.
- 핸들 보장은 낡은 핸들에 대한 것이지 위조된 핸들에 대한 것이 아니다.
  `(슬롯, 세대 + 1)`을 계산해 내는 프로그램은 지금 그 칸에 있는 노드를 가리킬
  수 있다. 핸들은 불투명한 값이라는 전제다.
- 당시 판은 루트 이름에 세대가 없고 렉시컬 스코프에 의존했다. 후속
  [루트 세대 개선](ownership_teardown_root_epoch_2026-10-08.md)은 재선언에서도
  옛 루트 identity를 거부한다. arena-domain binding과 권한 발급은 여전히 OPEN이다.
- 모델 밖: 동시성, 자원 finalizer 순서, 세대 상한(여기서는 무한한 `nat`이고
  은퇴 방식은 `OwnershipGraphLinks.v`에 있다), 자식 색인을 걷는 비용, 색인의
  메모리 비용.
- 위 저장소 모델과의 합성은 증명하지 않았다. 저장소 상대 링크를 쓰는 저장소
  안에서 노드 단위 소유 트리를 두는 형태가 후보다.

**레드팀 반영.** 1차 레드팀은 건전성 버그를 찾지 못했지만, 모델이 덜 다룬
곳을 지적했다. 모두 고쳤다.

- (High) 연산이 대상을 세대 없는 슬롯 번호로 지정했다. 그래서 해제된 노드의
  옛 핸들로 재사용된 칸의 남의 노드를 해제하거나 그 밑에 노드를 붙일 수
  있었다. 지금은 모든 대상이 세대가 맞는 핸들이어야 한다.
- (Medium) 루트에 수명이 없어서, 아무도 선언하지 않은 루트에 노드를 붙일 수
  있었다. 루트 생성·해제와 `RootsLive`를 넣었다.
- (Medium) 해제 단위를 구하는 방법이 힙 전체 열거뿐이었다. 자식 색인과
  `unit_from_kids`를 넣었다.
- (Medium) 참조 계수 반례가 공허했다(빈 루트에서 닿는 것은 원래 없다).
  "영원히"도 증명하지 않았다. 실제 참조 계수 단계 관계와 모든 단계에 걸친
  `rc_cycle_permanent`로 바꿨다.
- (Low) finalizer 규칙, 해체가 읽는 범위, "정확히 한 번"의 범위를 정리 내용에
  맞게 고쳐 썼다.

2차 레드팀은 새 불변식(루트 수명, 자식 색인)이 모든 단계에서 유지되고 공허하지
않으며, 노드 핸들·소유 포인터·두 색인 어디에도 재사용 경로가 남지 않았다고
확인했다. 참조 계수 비교도 공정하다고 봤다. 참조 계수 기계는 순환이 아닌
사슬은 실제로 해제하고, 같은 결과가 소유 모델 실행의 힙에서도 성립한다. 남은
지적은 이렇게 처리했다.

- (Medium) 루트 해제 단위는 여전히 힙을 훑어야 구할 수 있었다. 루트가 직접
  소유한 노드가 어느 색인에도 없었기 때문이다. 자식 색인을 소유자별로 바꾸고
  `root_unit_from_kids`를 넣었다.
- (Low) 루트 이름에 세대가 없다. 다시 선언된 루트가 옛 노드를 넘겨받지 않음을
  증명했고(`root_reuse_adopts_nothing`), 렉시컬 스코프 전제를 명시했다.
- (Low) 핸들 위조는 막지 않는다. 불투명 핸들 전제를 명시했다.
- 레드팀이 제안한 따름정리 `no_roots_no_nodes`를 넣었다.

**Qt와의 대응**

| Qt | 이 모델 |
|---|---|
| `QObject` 부모·자식 트리 | 노드의 owner 필드(`OParent`)와 루트(`ORoot`) |
| 부모를 지우면 자식도 지운다 | 해제 단위는 소유 서브트리 전부 |
| 스택 객체가 스코프를 벗어나면 자식까지 지운다 | `RootDrop` |
| children 목록 | 자식 색인(정확해야 한다) |
| 소멸 시 시그널 연결 자동 해제, `QPointer` 자동 null | 1단계: 역방향 색인으로 들어오는 링크 비우기 |
| 양쪽 끝에 유지하는 연결 목록 | 역방향 색인(정확해야 한다) |
| `deleteLater` | 이 모델은 2단계를 바로 한다. 회수를 미루려면 세대 올림(논리적 해제)은 1단계로 옮겨야 한다. 그러지 않으면 반례 5와 같은 창이 생긴다 |
