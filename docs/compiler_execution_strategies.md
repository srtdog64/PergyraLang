# 컴파일러 실행 전략 분류 (JIT / 트레이싱 / AOT)

목적: 컴파일러/실행 전략의 종류를 정리하고, 흔히 혼동되는 "트레이싱"과
"MIR(중간 표현)"을 분리하며, Pergyra 컴파일러가 어디에 속하는지 못박는다.

핵심 한 줄: **Pergyra는 트레이싱 컴파일러가 아니라, Rust/Swift 계열의 정적
다단(多段) IR AOT 컴파일러다.** "MIR"은 런타임 트레이싱이 아니라 정적 중간
표현(Mid-level IR)을 뜻한다.

---

## 1. 큰 그림: 코드 실행 전략

소스 코드를 실제로 돌리는 방식은 크게 셋이다.

| 전략                      | 언제 기계어/실행이 정해지나                       | 대표                                     |
| ------------------------- | ------------------------------------------------- | ---------------------------------------- |
| 인터프리터(Interpreter)   | 런타임에 AST/바이트코드를 한 단계씩 해석          | CPython(순수), 초기 Ruby                 |
| AOT 컴파일(Ahead-of-Time) | 실행*전에* 전체를 기계어로 컴파일               | C/C++, Rust, Swift, Go,**Pergyra** |
| JIT 컴파일(Just-in-Time)  | 런타임에 "뜨거운" 코드를 그때그때 기계어로 컴파일 | V8(JS), HotSpot(JVM), .NET CLR           |

대부분의 실제 런타임은 이들을 섞는다(예: JVM = 바이트코드 인터프리터 +
JIT). 중요한 구분은 "기계어 생성이 빌드 타임이냐(AOT) 런타임이냐(JIT)"이다.

---

## 2. AOT 컴파일러와 다단 IR 파이프라인

AOT 컴파일러는 보통 소스를 한 번에 기계어로 바꾸지 않고, *점점 낮은 수준의
중간 표현(IR)* 으로 단계적으로 낮춰간다(lowering). 이렇게 단계를 두는 이유:

- 각 단계가 한 가지 관심사만 책임진다(파싱 / 타입검사 / 최적화 / 코드 생성).
- 최적화와 분석을 IR 수준에서 한 번 하면 여러 백엔드가 공유한다.
- IR이 단일 진실원(single source of truth)이 되어 백엔드가 AST를 다시 읽지
  않는다.

대표적인 다단 IR 파이프라인(전부 현대 주류, 폐기된 기법이 아님):

- **Rust**: AST -> HIR -> MIR -> LLVM IR -> 기계어
- **Swift**: AST -> SIL(Swift Intermediate Language) -> LLVM IR -> 기계어
- **LLVM** 자체가 IR(LLVM IR) 중심 파이프라인
- **Pergyra**: 소스 -> AST -> HIR -> MIR -> AIR -> 코드젠(C 트랜스파일러 / LLVM)

여기서 **MIR = Mid-level Intermediate Representation**(중간 표현)이다. 이름이
Rust와 같지만 우연이 아니라 같은 설계 계보다. **런타임 트레이싱과는 아무
관계가 없다.**

---

## 3. JIT 컴파일러: 메서드 기반 vs 트레이싱

JIT은 런타임에 코드를 컴파일한다. "무엇을 컴파일 단위로 잡느냐"에 따라 둘로
갈린다.

### 3.1 메서드(함수) 기반 JIT  — 현재 주류

- 단위: 함수/메서드 하나 전체.
- 동작: 인터프리터로 돌다가 자주 불리는 함수(hot)를 통째로 기계어로 컴파일,
  필요하면 더 공격적으로 재컴파일(티어업).
- 대표: V8(JS), HotSpot(JVM), .NET CLR, LuaJIT의 일부.
- 현재 사실상의 표준. 분기 많은 일반 코드에 안정적.

### 3.2 트레이싱 JIT  — 대부분 폐기된 기법

- 단위: *런타임 실행 경로(trace)* 하나. 보통 뜨거운 루프의 한 번 실행을
  선형으로 기록한다.
- 동작: 인터프리터가 루프를 돌며 실제로 지나간 명령 시퀀스를 "트레이스"로
  녹화 -> 그 선형 트레이스를 컴파일 -> 다음부터 조건(가드)이 맞으면 그
  기계어로 점프. 가드가 깨지면 인터프리터로 되돌아간다(side exit).
- 대표: **TraceMonkey**(옛 Firefox JS 엔진), **Dynamo**(HP), **PyPy의
  메타-트레이싱**, 초기 LuaJIT 트레이스.

**왜 대부분 폐기/축소됐나:**

1. 트레이스 폭발: 분기가 많으면 경로 조합이 폭발해 트레이스가 너무 많아진다.
2. 가드 실패 비용: 실제 실행이 녹화된 경로를 벗어나면 자주 되돌아가야 한다.
3. 다형성/예측 불가 분기에 약함(웹 JS 같은 실코드에 불리).
4. 메서드 기반 JIT(V8 등)이 인라이닝 + 추측 최적화로 더 견고하게 이김.

결과적으로 Firefox는 TraceMonkey를 버리고 메서드 기반(JägerMonkey ->
IonMonkey)으로 갔다. 그래서 "트레이싱 컴파일러는 보통 폐기됐다"는 말은
*트레이싱 JIT*에 대해선 정확하다. (PyPy의 메타-트레이싱처럼 살아있는 사례도
있지만 주류는 아니다.)

---

## 4. 흔한 혼동: "MIR/lowering"은 트레이싱이 아니다

|                       | 트레이싱 JIT          | 다단 IR AOT(우리)            |
| --------------------- | --------------------- | ---------------------------- |
| 컴파일 시점           | 런타임                | 빌드 타임                    |
| 단위                  | 실제 실행한 선형 경로 | 정적 프로그램 전체 구조      |
| "MIR"의 의미          | (해당 없음)           | Mid-level IR(정적 중간 표현) |
| 되돌아가기(side exit) | 있음                  | 없음                         |
| 대표                  | TraceMonkey           | Rust, Swift, Pergyra         |

"본문을 MIR로 낮춰서 코드젠이 MIR을 읽는다"는 것은 *정적 다단 컴파일의 정상
동작*이지 트레이싱이 아니다.

---

## 5. Pergyra는 어디에 속하나

- **정적(AOT) 다단 IR 컴파일러.** 트레이싱 아님, JIT 아님(현재).
- 파이프라인: 소스 -> AST -> HIR -> MIR -> AIR -> 코드젠(C 트랜스파일러 /
  LLVM).
- 설계 계보: Rust(HIR/MIR), Swift(SIL)와 같은 현대 주류.
- 불변식: 함수 본문은 MIR을 거쳐 내려간다(non_cfg_body_fallback == 0,
  "MIR-or-abort"). 즉 **코드젠은 AST가 아니라 MIR을 단일 진실원으로 읽는다.**

### 실무 함의 (왜 이게 중요한가)

이 설계 때문에, 어떤 기능을 *AST-emit 계층*에만 구현하면 MIR 경로에서
바이패스되어 런타임에 동작하지 않는다. 실제로 transaction 사가(`fail` ->
역순 `compensate`)가 AST-emit에만 있어서, 본문이 MIR로 내려가는 순간
무시되어 보상이 실행되지 않았다(컴파일은 통과, 런타임에 saga 미작동). 올바른
구현 위치는 **MIR-CFG 레벨**(hir_lower_cfg + mir)이다. 이것은 트레이싱과
무관하며, 오히려 "MIR이 단일 진실원"이라는 올바른 정적 설계의 결과다.

---

## 6. 용어 빠른 참조

- **AOT**: Ahead-of-Time. 실행 전 전체 컴파일.
- **JIT**: Just-in-Time. 런타임에 뜨거운 코드 컴파일.
- **인터프리터**: 런타임에 한 단계씩 해석.
- **IR**: Intermediate Representation. 컴파일 중간 표현.
- **HIR / MIR / AIR**: High / Mid / (프로젝트 고유) Analysis-or-Artifact-level
  IR. 정적 단계별 표현이며 트레이싱과 무관.
- **트레이싱 JIT**: 런타임 선형 실행 경로를 녹화해 컴파일하는 기법. 대부분
  메서드 기반 JIT에 밀려 폐기.
- **메서드 기반 JIT**: 함수 단위로 런타임 컴파일. 현재 주류.
- **side exit / 가드**: 트레이스 실행 중 조건 불일치 시 인터프리터로 복귀.
- **lowering**: 높은 수준 IR을 낮은 수준 IR로 단계적으로 변환.
