# Intrinsic Template Design Goals

## 1. 배경

Pergyra는 AI가 직접 쓰기 쉬운 언어를 지향한다.
하지만 AI가 긴 보일러플레이트를 매번 안정적으로 생성하는 것은 어렵다.
특히 다음 문제들이 반복된다.

- 호출 순서가 중요한 패턴을 자주 틀린다.
- 런타임 규약을 빠뜨리기 쉽다.
- 비슷한 코드가 프롬프트마다 미묘하게 달라진다.
- 에디터/LSP가 없는 환경에서는 스니펫 기반 접근이 작동하지 않는다.

따라서 Pergyra는 일부 패턴을 intrinsic template로 언어 내부에 내장한다.

## 2. 정의

`intrinsic template`는 다음 특성을 가진다.

- 표면에서는 함수 또는 생성자처럼 보인다.
- 실제로는 컴파일러가 알고 있는 확장 규칙을 가진다.
- 확장 결과는 일반 AST/HIR 노드로 환원된다.
- 확장 이후에는 일반 코드와 동일한 시맨틱 규칙을 적용한다.

예시:

```pergyra
let user = HttpGetJson<User>(url);
```

위 호출은 단순 라이브러리 함수 호출이 아니라, 요청 생성, 응답 검증, 디코드, 오류 포장 같은 보일러플레이트를 포함한 템플릿 확장 대상으로 볼 수 있다.

## 3. 목표

### 3.1 AI가 짧게 쓰기 쉬워야 한다

모델은 장문의 구조보다 짧고 일관된 표면 API를 더 안정적으로 생성한다.

```pergyra
let result = HttpGetJson<PlayerProfile>(profileUrl);
```

### 3.2 확장 결과는 컴파일러가 검증해야 한다

템플릿 확장은 문자열 치환이 아니라 구조적 변환이어야 한다.
확장 이후 타입 검사, 효과 규칙, 런타임 규약 검증이 이어져야 한다.

### 3.3 언어 의미를 감춰서는 안 된다

intrinsic template는 "마법"이 아니라 축약이다.
필요하면 확장 결과를 사용자가 이해하고 추적할 수 있어야 한다.

### 3.4 초기 범위는 작게 시작한다

범용 매크로 시스템부터 도입하지 않는다.
AI 사용 빈도가 높고 패턴이 안정적인 영역부터 제한적으로 시작한다.

## 4. 비목표

- 임의 문자열 기반 코드 생성 도구를 만드는 것
- 모든 라이브러리 패턴을 intrinsic으로 승격하는 것
- 문법 전체를 AI 전용 DSL로 바꾸는 것
- 에디터 플러그인 없이는 사용할 수 없는 기능을 핵심으로 삼는 것

## 5. 외부 스니펫 방식과의 차이

외부 API 또는 에디터 스니펫 방식은 다음 한계가 있다.

- 에디터 의존성이 생긴다.
- 스니펫 확장 결과가 컴파일러 의미 체계와 느슨하게 연결된다.
- AI가 어떤 스니펫 이름을 언제 써야 하는지 외부 문맥에 의존한다.

반면 intrinsic template는 언어 내부 계약이다.

- 호출 이름이 곧 언어 의미다.
- 컴파일러가 직접 인식한다.
- LSP 없이도 동일하게 동작한다.

## 6. 첫 설계 원칙

### 6.1 정규 이름을 사용한다

AI가 흔들리지 않도록 별칭을 남발하지 않는다.

### 6.2 확장 후 일반 코드로 환원한다

별도 런타임 마법 레이어를 최소화한다.

### 6.3 진단 가능해야 한다

사용자가 intrinsic template 사용 중 무엇이 확장되었는지 추적할 수 있어야 한다.

### 6.4 엔진 코어 우선

Pergyra의 코어 방향과 맞는 템플릿부터 채택한다.
즉, 메모리, 동시성, 이벤트, 시스템 통합처럼 반복되지만 규약이 강한 영역을 먼저 본다.
